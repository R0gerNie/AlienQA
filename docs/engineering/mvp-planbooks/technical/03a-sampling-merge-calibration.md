## 1. 要解决的问题与关闭边界

首轮 samples=2 的四个控制案例、五个动作全部因采样合并未决，没有进入 judge。当前 `merge_samples` 以 `(basis.type, basis.reference)` 分组，要求组内各采样的**文本集合完全相同**。它把措辞差异当成要求分歧，还可能在 A 对 A+B 时连共同的 A 一起丢掉。

真实例子来自 variant=2、ST-00001，依据均为“点击保存后可以查看操作结果。”：

> 点击「保存」后，界面应提供可观察的操作结果反馈，使我能判断保存是否成功、失败或因当前条件无法完成；不限定反馈形式。

> 点击保存后，界面应提供可观察的操作结果反馈，使我能判断保存是否成功、失败或因当前状态无法完成；不限定反馈形式。

这对文本可以作为有限反馈规则的校准候选；不能由此推导所有五对都是同义。variant=3 的一份输出多了“若账户标识暂不可用”的条件，需要单独确认它是可接受例子、附加要求还是无法支持的业务推测。

本副计划要让**已能解释的同义要求进入判定，未提及不算反对，真正冲突和无法确定的关系保留为未决**。合并只整理事前要求；它不证明模型提出的要求正确，也不使用动作后的反馈来挑选预期。

关闭本副计划意味着合并契约、回归、保存/报告接线及有界控制样例校准完成。N06 仍需真实小应用、独立人工复核；本计划通过不能替代这些条件。产品仍面向单人独立开发者，不扩展岗位画像或企业配置。

## 2. 本轮选定的技术路径

采用**有限、可解释的确定性规则 + 未覆盖关系保留未决**，第一批只处理“当前动作的可见操作结果反馈”。规则覆盖范围以校准语料确定，既不承诺通用自然语言等价，也不直接用字符串相似度阈值。

处理顺序：

1. 沿用 N02 对 JSON、条数、长度和原文依据的验证；非法引用不能通过归一化获得合法身份。
2. 将每条原文标记为 `(sample_index, row_index)`，以冻结的本次动作限定作用范围，保留原始 text/basis。
3. 仅做不改变要求的排版归一化；随后尝试有限反馈规则。每个规则必须说明支持的动作、目标、结果、条件、强制程度和反馈形式限制，并能解释整条文本。只命中“反馈”等关键词不足以归类。
4. 对候选要求逐条比较，区分等价、兼容独立、冲突、未知；没有明确关系不能自动组成等价组。一个成员与 A 等价、与 B 未知时，不能凭相似度传递把 A/B 一起合并。
5. 对归并候选组检查五条上限，超限显式失败；关系筛选后对可接纳组选择一条原始 text/basis 作为代表，保存全部成员及规则命中记录，未决组另存；交给 `ExpectationEngine.expect` 分配并冻结 ID。

最小规则模块放在 `alienqa/expectation/`，由 `contracts.py` 调用；不要把词表、匹配和状态汇总继续堆进角色提示函数。初期规则在代码中版本化，不增加面向用户的规则编辑器。

明确不采用：额外 LLM 语义裁判、embedding/向量库、多数票“正确答案”、无依据的模型自报 semantic_key。这些会新增成本或另一层无法验证的判断，不能作为本次解锁判定的前提。模型输出仍为 text + expectation_basis；本轮不增加模型必填分类字段。

### 2.1 有限规则如何避免放宽要求

- “保存后应说明操作结果”与“保存后应有可见结果反馈”：只有整句可归入同一反馈契约、动作与条件一致时才合并。规则名建议 `operation_feedback`，不得仅凭共同 basis 合并。
- “不限定形式”“例如按钮变化或状态说明”可以表达可选实现；“必须出现 toast”“必须变为已保存”表达更强要求。后者不能被删掉再归入通用反馈。
- “成功、失败或暂不能完成应有说明”不等于“必须保存成功”。成功态、否定、条件、数值、时限、对象和前序步骤引用必须保留；不得通过去掉否定词或业务名词制造同义。
- 当前动作“保存”和“保存下一项”在不同 step 中绝不比较。相同 step 内提到另一个控件、对象或历史行为时，须证明作用对象相同；不能仅靠按钮文案相似推断。
- 规则不能解释的余句、复合要求或条件分支会使该关系退回未知。第一版不强拆自然语言里的“且/或”，不承诺识别所有单样本内部矛盾。
- 每条规则需有同义正例、限制增强反例和未知边界例。增加覆盖须同时补这些样例，不能只扩同义词表。

泛化后的契约用于比较，不替换用户看到的原文，不传给 judge 作为新的“标准答案”。代表原文按固定排序选取，不按先返回的采样或动作后的结果选取。规则不支持的原文仍可保持原身份；一旦需要判断它与另一条的关系却无法确定，就保留未决。

## 3. 采样合并决策契约

这里的 A/B 表示要求，不是字符串；下表的分类需有规则或原文一致性支持，否则采用未知分支。

| 情形 | 合并规则 | 需要保留的解释 |
|---|---|---|
| 同一要求、同义改写 | 合为一条原文代表 | 每份原文、依据、成员索引、规则版本及命中理由 |
| 采样一为 A，采样二为空 | 接纳 A，支持数为 1 | 未提及不是反对，也不是双采样共识 |
| 采样一为 A，采样二为 A+B | 保留共同 A；B 独立评估 | B 缺席不淘汰 A；B 与 A 的关系未知时只将受影响部分未决 |
| 同一依据下两个可证明兼容的独立要求 | 分别保留，不强合成一句 | 单条支持数及兼容规则；没有证明兼容则未决 |
| 相同对象、相同条件下互相排斥 | 受影响要求均未决 | `conflict`；列出冲突成员，不取多数票 |
| 条件不同、对象不同或只是措辞相近 | 不直接推断冲突/等价 | 无法证明独立或等价时 `relation_unknown` |
| 完全相同 text、不同有效 basis | 可去重为一条，选一个原始有效 basis | 所有来源 basis 保存在合并 provenance，不伪造综合 reference |
| 同义 text、不同 reference / basis 类型 | 仅在有限规则证明同一要求且各引用独立合法时去重 | basis 不作为要求身份；无法证明关系则未决，不全局抛错 |
| 同一采样内明确矛盾 | 同样进入关系检查，不要求跨采样才触发 | 支持范围内标 conflict；未覆盖的表达只披露能力限制 |
| 任何采样解析失败、超时或中断 | 本步预期生成不完整；沿用 failed/取消诊断，不当作空数组 | 已返回原文保留，但不把失败样本计入共识或交付完整集合 |
| 原始 JSON 非法、依据不合法、单份超过上限 | 沿用 N02 失败契约 | 不通过吞掉非法条目获得合并成功 |
| 归并后的候选组超过五条 | 显式生成失败，在关系筛选前检查候选上限，不按支持票或前五条静默截断 | 保留所有候选及 `merged_limit_exceeded` 诊断，不通过未决筛选绕过上限 |
| 所有成功采样都为空 / 所有要求未决 | 不调用 judge，认知 inconclusive | 空集合不能代表操作通过 |

对未知要求不能直接作并集并交给 judge；对有效的独立组也不能因另一组未知而全部清空。样本数 1/2/3 均沿用同一契约，支持数只表明出现次数，不是置信度或正确率。

## 4. 数据、身份与部分检查

### 4.1 合并诊断最小增量

沿用 `last_generation` 和步骤 `expectation_generation`，保持 raw/samples/unresolved 的可读性；以下字段已接入：

| 字段 | 语义 |
|---|---|
| `merge_version` | 独立于 prompt 的合并版本；旧算法离线基线为 `sampling-merge-v1`，初版规则为 `sampling-merge-v2`，新增真实词形回归后为 `sampling-merge-v2.1`；旧记录缺字段仍显示未记录 |
| `sampling` | requested / returned / validated 数量及 complete；失败不能算未提及 |
| `groups` | 每组代表 text/basis、成员 sample_index/row_index、支持数、rule_id、关系决定及理由 |
| `unresolved` | 保留原 texts/basis 兼容字段；增补成员引用和 reason_code，区分 conflict / relation_unknown |
| `coverage` | complete / partial / none，仅表示已生成要求的处理覆盖，不表示产品全部能力已测试 |

成员以保存的样本为来源；T08 的 call_id 如果当前接口能提供则关联，不能伪造历史 call_id。raw 截断标记必须保留，不能把截断原文当作完整回放材料。关系比较使用已经验证的完整 parsed 数据；缺 parsed 时不要从截断文本补造要求。

`Expectation` 和 `Evidence` 仍各只有一个 basis 对象，其他支持依据留在生成诊断中，不改成第二套证据模型。组代表按稳定 text/basis 排序选取，最终集合固定排序后沿用 `EX-{step_id}-{index}`。成员及规则记录必须能关联到该 ID。

身份在动作执行前一次性冻结；执行后不能重新合并、换代表文本或重编号。历史 run 不改写，不以新规则重渲染成新结论。离线回放产物另存，明确它是算法对照，未生成新事前预期或认知 Evidence。

若提示没有改变，继续标 `general-user-v1`，只改变 merge_version；若确需修改生成提示则单独升版，并使 `contracts.PROMPT_VERSION`、实际 `_invoke` 元数据和持久化值一致。`judgment-v2` 独立记录，不能把 judge 修复收益归因于合并规则。

实施增量：词形扩展仍不足以稳定恢复真实采样，因此生成提示已独立升为 `general-user-v2`。仅对模型自主提出、无额外条件/对象/时限/结果/实现限制的一般反馈要求规范原文表达，保留 text + basis 接口；有额外限制时必须完整表达，不要求每个动作提出通用反馈。原 v1 批次不改写，新提示收益单列。

### 4.2 部分检查不能变成完整通过

当前 Pipeline 只检查是否形成非空 expectations，随后可用 judge 结果覆盖步骤状态；因此“部分接纳 + 部分未决”需要补接线，不能仅修改 `merge_samples`。

- 完整采样、存在接纳组且无未决：沿用现有四态判定路径。
- 有接纳组且有未决：允许 judge 检查已冻结的接纳组，保存 judge 原始结果，并记录 `coverage=partial`。
- 局部 judge passed：步骤 `cognitive_status=inconclusive`，说明“已检查要求满足，但仍有采样要求未决”；保留局部 passed，不计入完整可用判定数。
- 局部 judge mismatch：保留该 mismatch 与其 Evidence，步骤可为 mismatch，同时明确 partial；报告不能暗示其他要求均已满足。
- judge failed/inconclusive：保留对应状态；覆盖标记不能把失败改为通过。动作失败、观察缺失和生成失败仍遵守现有边界。

T06 在线步骤诊断与离线 analysis 同时显示：采样完成情况、检查覆盖、局部判定及未决原文/原因。confirmed 保持现有审核规则。不得只在 scan.json 存字段而让产品页面继续展示无说明的 passed。

技术采证仍先落盘，预期或判断故障不丢技术候选。T04 的增量提交需保存每份样本和最终合并诊断；中断前的有效前缀可读，不能在退出时补一份“成功合并”。

## 6. 回归矩阵与真实模型复跑

### 6.1 零新增模型调用的工程验收

先用本机已有输出做新旧算法对照，再把最小脱敏片段与构造例存入仓库。每个标签标记“人工待复核”或实际复核来源；助手拟定标签不能冒充独立人工验收。

| 样例族 | 必查结果 |
|---|---|
| 五对首轮真实输出 | 分别标注，不能预设 5/5 全部恢复；记录同义恢复、条件差异、未知原因 |
| 同义改写、标点差异、完全重复 | 支持范围内稳定去重，代表仍是原文 |
| A/空、A/A+B、兼容 A+B、未知附加 B | 未提及不反对；共同 A 保留；未知不默认为兼容 |
| 普通反馈/强制 toast、成功/成功或合理校验 | 不放宽限定，不把保证成功换成可接受失败 |
| 否定、条件、对象、时限、数值差异 | 不因文本相似合并；支持范围外关系未知 |
| 同 basis 不同要求、跨 basis 同要求、相同 text 多依据 | basis 不是语义身份；独立保留或未决，不因单个碰撞全局报错 |
| 同采样内矛盾、跨采样矛盾、样本/行顺序交换 | 在规则支持范围内阻断冲突；输出身份稳定，不按多数票选择 |
| samples=1/2/3、解析故障、超时/停止、输出截断、合并超过五条 | 完成数/支持数诚实，失败不退化为空，边界诊断不丢 |
| 接纳+未决：局部 passed / mismatch / failed | 状态与覆盖规则正确，局部 mismatch 留 Evidence，技术证据照常保存 |
| 旧 run、旧文本调用、新 run 保存/读回、离线 HTML | 缺字段可读，原记录不变；新字段与实际诊断一致 |

对应回归放在现有 T03、pipeline、RunWriter、T06 和 N06 测试中，只增加必要路径测试。以受控边界全部满足为工程 gate，不把测试标签命中率包装成真实用户准确率。

### 6.2 真实模型验收协议

本轮用户已明确选择新增 100 次 CLI 启动硬上限；历史首轮 40 次另计。本轮初版定向 20 次、v2.1 完整控制样例 42 次、新提示定向 30 次、合理校验 6 次，合计 98 次；余 2 次未使用。每批冻结配置、prompt/合并版本与上限，修复/失败/调查/reporter 共用预算；本轮已结束，后续模型复跑需独立预算。

1. **离线隔离合并变量**：对相同保存采样分别运行 v1/v2，不调用 judge；逐组记录接纳/未决变化。这是算法回放，不能推导完整认知判断改善。
2. **正常/缺反馈小批次**：variants=1/2、samples=2、repeats=2，固定模型配置和 `judgment-v2`，保存四个独立 run。不要把 samples=1 当作恢复双采样的替代。
3. **全部控制样例**：上一阶段无错误放宽后，再跑 variants=1～4、samples=2、repeats=2，包含前序历史的两步路径。应用、prompt、merge、judge 版本单列；与旧 judge 的首轮基线不能作单变量效果比较。
4. **独立复核**：核对每条要求的合理性、等价/冲突标签、实际可见结果及判断；对合理校验和条件分支重点复核。控制样例通过后仍按 N06 接真实应用。

每批输出至少包含：计划案例/run/动作数，实际启动与完成数，生成/解析失败数，采样完整数，接纳及未决组数，complete/partial/none 步骤数，完整可用判定数、局部判定数和判定失败数，费用已知/未知及停止原因。未决细分为冲突与关系未知；`not_started`、cancelled、failed 都留在计划分母中。

控制样例最低通过条件：正常/缺反馈两个案例各两次重复均取得完整采样和可复核判定；正常的等价反馈不因形式被判落差，缺反馈能通过合法 ID/text 引用形成认知落差；合理校验不被强制要求成功，前序引用不越界。每个要求另核对依据与合理性，不能靠正确状态掩盖错误预期。任一条件不满足保留开放原因；不通过删除失败运行或强吞条件分支满足 gate。
