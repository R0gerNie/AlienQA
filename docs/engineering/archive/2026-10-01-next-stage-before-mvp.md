> 编写及本轮验证更新日期：2026-10-01。本文是基于现有产品规划、模块计划和工程文档的强化计划，不是全部原承诺的完成声明。

## 1. 项目定位、范围与完成定义

AlienQA 为前端开发者和测试人员提供“以陌生用户的自然预期发现可疑交互，再由人类定性”的辅助测试流程。依据 [总体计划 §1、§2](../../PLANBOOK.md)，其核心价值是发现技术异常和交互不清晰，并交付团队可以复现、核对和定位的问题。它的责任止于可疑证据、调查假设和人类审核后的报告，不把模型判断直接当成产品缺陷定论。

下一阶段保留这条链路：**接入被测应用与登录态 → 形成受限产品介绍 → 在当前状态选择动作 → 为该动作形成预期 → 执行并采集前后证据 → 明确记录判定成功或失败 → 聚类与回放 → 调查 → 人工审核 → 交付报告**。用户能解释一次扫描覆盖了什么、哪里没有完成、为什么采信某条问题，并让另一个人在相同环境重现结果，才算闭环成立。

本阶段核心必需项是动作与预期绑定、失败可见、真实状态探索、完整证据与回放、审核和报告一致性。真实框架测试、模型效果评估、依赖与 CI 是必要支撑。团队共享运行、外部工单写入和商业权限可以延后；是否进入它们由阶段证据决定，不沿用总体计划中的旧人日估算作为当前承诺。

本次已读并核对 [总体计划](../../PLANBOOK.md)、[模块索引](../../planbooks/README.md)、01～13 全部模块计划、01b/02b/11b 全部黑盒变体，以及 [治理](../governance.md)、[商业化](../commercialization.md)、[基线](../baselines.md) 文档。下表“已核对”仅表示相关规划与消费关系已阅读，不表示实现或运行验收通过。第三方仓库的版本、依赖、运行命令和许可描述取自基线文档快照，本次未联网重新验证。

## 3. 关键挑战与可落笔的规则

以下评审角色是模拟视角。优先级表示进入相应阶段前必须解决的后果，不是已发现实现故障的数量；本轮修复是否关闭挑战以 §8 的证据为准。

### C01 [P1] 单元指令会不会把“陌生人”变成按内部规则测试的人？—产品与效果评估视角

**依据与影响**：总体 §1.2、§4.3 和 03 禁止内部规则；当前产品又接受测试单元和指令。指定“测登录区域”与提供“正确密码必须跳转某页”对自然预期的影响不同。若混在同一个模式里，benchmark 和报告无法解释发现来自用户直觉还是人工用例。

**组员质问**：“当用户把预期答案写进单元指令，这个结果还能被称为零培训用户的发现吗？”

**作者最佳回应**：

> “不把人类团队对系统的"第一印象"注入 LLM”——[总体 §1.2](../../PLANBOOK.md)。
> “源码只给"加载器/角色A"看，角色B/C 永远看不到源码。角色B/C 只能拿到 `gist` 主旨 + 截图。”——[总体 §4.3](../../PLANBOOK.md)。
> “白名单/黑名单做成配置，未来可收紧或放宽。”——[03 §4](../../planbooks/03-exploration-context.md)。

检查：引文占比达标，回应正文为逐字引文；事实一致性通过，均为规划约束；回应部分，未定义用户指令属于范围提示还是规则注入。

**追问与判断**：部分成立，属于模式定义缺口；可配置边界不能消除结果口径差异。建议在 03、CLI/UI、报告与评估 manifest 中统一标识 `intuition` 与未来的 `guided` 模式。默认 intuition 只把区域/导航范围作为探索限制；含内部业务正确答案的指令须明确转为 guided 并在报告标注，不能混入自然预期效果表。代价是一次模式说明和必要的指令分类，不需要本阶段增加完整用例平台。

**关闭条件**：同一应用分别给范围提示和内部答案，角色输入记录可核对，模式标签贯穿证据与报告；两类 benchmark 分开。建议产品/评估职责在 G1 前确定模式规则，G2 验证。

### C02 [P0] 动作、预期、观察和判定失败必须属于同一次可核对交互—验收视角

**依据与影响**：总体 §4.1 要求先预期再执行；08 的“先观察后预期”标题又可能被理解为看结果后形成预期。判定 API 出错、返回非法结构或超时若被折叠成无 mismatch，会把未判定交互误当成功检查，直接破坏可信结果门槛。

**组员质问**：“你拿的是这个保存按钮点击前的预期，还是整页任意预期？判定器坏了，界面会显示没有问题吗？”

**作者最佳回应**：

> “角色B 生成朴素预期 → 驱动执行操作 → 截图 → 采集信号”——[总体 §4.1](../../PLANBOOK.md)。
> “预期生成不读 Observation 细节，避免"顺着结果找理由"。”——[08 §4](../../planbooks/08-expectation-engine.md)。
> “判定输入只含 `action + before/after + expected + 技术信号`，不含源码。”——[08 §7](../../planbooks/08-expectation-engine.md)。

检查：引文占比达标；事实一致性通过，指的是预期设计；回应部分，未定义绑定、判定失败与 run 完整性。

**争点覆盖**：先于执行形成预期已有明确依据；当前动作的绑定和失败状态仍需契约。建议一次 step 持有 `step_id/state_before/action/expectations/execution/observation/judgment/state_after`。预期只能用当前状态和已选择动作的允许信息形成，随后执行该动作；定位失败、观察缺失、判定失败分别记录，不生成“已通过”判断。run 概览同时报告执行、判定成功、判定失败及未判定步数；无证据但存在失败的 run 显示“检查不完整”，禁止显示“未发现问题”等同验证通过。

**关闭条件**：两个按钮有不同预期；模型返回非法 JSON、超时或耗尽 fallback 时，证据和状态不串位，失败可见，所有步数有可核对分母。建议流水线/LLM/验收职责在 G1 联合验收。

### C03 [P1] 静态按钮遍历不能替代状态图上的主动探索—执行视角

**组员质问**：“保存按钮只有填完表才出现，modal 又换了候选集；你在初始页找到的按钮清单如何代表这条路径？”

**作者最佳回应**：

> “面对"当前状态 + 当前页面 + 已经探索过什么"，回答：**下一步干什么最有价值**。不是"把所有按钮点一遍"。”——[06 定位](../../planbooks/06-action-planner.md)。
> “记录 `parent` 与触发 `action`，保证可回溯。”——[05 §4](../../planbooks/05-state-tracker.md)。
> “从当前页面提取可交互元素作为候选集。”——[06 §7](../../planbooks/06-action-planner.md)。

检查：引文占比达标；事实一致性通过；回应部分，方向正确，但完整路径的候选刷新、状态去重与覆盖口径须集成证明。

**判断与修改**：待验证假设；05/06 的局部完成不能证明主流水线使用了相同策略。建议每次执行后重新观察状态和候选；同一元素在不同状态可产生新动作，已尝试集合按“状态＋动作”定义。状态签名保留业务上有意义的 tab/modal/counter 等差异，去噪只去动态噪声。同时保留访问序列与去重后的图，不因节点合并丢失完整 replay 前缀。输入、select、hover、press、goto 按场景接入，不把“动作类型已支持”计作“该路径已探索”。

**关闭条件**：多步表单、tab/modal、分页或路由变化的固定 fixture 走通；状态图可往返读取；预算耗尽准确记录未探索区域和终止原因。建议 04/05/06 职责在 G1 完成 fixture，G2 验证真实 SPA。

### C04 [P0] 完整回放包与“缺陷已复现”是两项不同的承诺—开发接收者视角

**组员质问**：“需要先打开订单再点击退款的证据，起点与前置动作在哪里？回放后的正常页面看起来也很像原图，会不会被标成复现成功？”

**作者最佳回应**：

> “每条 Evidence 必须含 `replay` 字段，否则视为不完整证据。”——[09 §4](../../planbooks/09-evidence-engine.md)。
> “回放 = 重放 Action sequence + 还原会话态”（cookies/session + viewport + browser 版本）。——[13 §4](../../planbooks/13-replay-engine.md)。
> “回放在隔离环境执行，避免残留状态影响。”——[13 §7](../../planbooks/13-replay-engine.md)。
> “`reproduced = match_score ≥ 0.7 或 信号命中`”——[13 §10/S6](../../planbooks/13-replay-engine.md)。

检查：引文占比达标；事实一致性通过；回应部分，提供环境还原思路，但宽泛相似度或信号不足以证明同一缺陷。

**判断与影响**：成立，属于证据就绪和复现结论定义缺口。09→13→11/12 都依赖此结果。建议分开记录“包完整”“回放执行完成”“问题条件匹配”；每条证据标明初始 URL、应用版本/构建标识、环境、会话引用、前置动作及目标动作。回放完成后以证据的特定异常/可见状态条件评估，图像相似度仅作辅助。结果至少区分 `reproduced/not_reproduced/blocked/error`；会话过期或环境不匹配归 blocked，不解释为偶发、不自动降低问题真实性。会话文件可以供本机回放使用，分享报告提供重新登录说明，不把会话秘密直接打包给外部接收者。

**建议补写**：“证据发布前检查 replay 前置字段和 artifact 可读性；不可满足时保留可疑发现并标为证据不完整。回放在新的浏览器上下文执行完整路径，只有原问题条件再次出现才标记 reproduced。原始证据不被回放产物覆盖。”

**关闭条件**：多步缺陷、正常相似页面、过期会话、缺 artifact 四类场景给出不同且可解释结果；原始与回放产物分别可见。建议证据/回放职责在 G1 接通，G2 校准匹配规则。

### C05 [P1] 相似证据归并不能提前保证同根因，调查上下文必须按 Issue 接收—调查与审阅视角

**组员质问**：“两个不同接口都白屏，你在哪一步证明它们同根因？调查第二个 Issue 时，怎样保证没有沿用第一个的 DOM 和 console？”

**作者最佳回应**：

> “对 Evidence 做 embedding / similarity → cluster → **Potential Issue**。”——[10 §1](../../planbooks/10-evidence-deduplicator.md)。
> “输出 Issue，可人工合并/拆分。”——[10 §4](../../planbooks/10-evidence-deduplicator.md)。
> “`Issue`（10）+ 关联 Evidence + **专家上下文（可看源码）**。”——[11 §2](../../planbooks/11-investigation-agent.md)。
> “根因降级为"行为根因"：黑盒看不到组件名”——[11b §4](../../planbooks/11b-investigation-browser.md)。

检查：引文占比达标；事实一致性通过；回应部分，允许候选和人工纠正，但需把关联、来源与未证实状态落实到消费契约。

**判断与修改**：部分成立，10 的“同根因”目标须通过标注验证，不能作为聚类算法天然属性。建议保留 Evidence 原始项、Issue 成员与聚类理由；调查只消费当前 Issue 关联证据，在独立回放后采集该路径的 DOM/信号，或明确标记历史记录来源。source mode 的检索以路由/相关文件和预算约束，blackbox mode 不输出声称已证实的源码组件根因。记录假设、支撑证据和仍缺证据。人工拆分/合并后使关联调查和报告失效或重新审核，不静默沿用旧假设。

**关闭条件**：同现象不同根因、同根因跨页面、两 Issue 连续调查三类样本；成员归属和专家输入可追溯，错误聚类可撤销。建议去重/调查/审核职责在 G2 联合验证。

### C06 [P1] 审核对象、终态与可交付报告需要一个一致的产品规则—审阅者与交付视角

**组员质问**：“原计划能备注、设计如此、跳过，归档又只给二态开关且阻止这些状态出报告。审阅者看到的到底是证据还是 Issue？报告能离开这台电脑阅读吗？”

**作者最佳回应**：

> “人工逐条审核 Issue（确认问题 / 误报 / 设计如此 / 跳过）。”——[12 §1](../../planbooks/12-human-review-report.md)。
> “保留 planbook 四态（confirmed/rejected/by-design/skipped），但 **UI 只暴露二态 switcher**（采信→confirmed / 不采信→rejected）；**报告生成前若有证据仍处于 by-design/skipped/pending，拒绝生成**。”——[12 §10](../../planbooks/12-human-review-report.md)。
> “**Jinja2 模板 → HTML**；再经 Playwright `page.pdf()` 导出 PDF。”——[总体 §5.5](../../PLANBOOK.md)。

检查：引文占比达标；事实一致性通过，保留了归档决策的限制；回应部分，给出了本期取舍但与全量审阅承诺及导出交付还有差距。

**判断与修改**：审核五态/二态是已明确的阶段取舍，不把二态本身定为程序故障；进入可交付审阅阶段前须显式调整规则。建议 Issue 为默认审阅组，Evidence 可逐条查验；成员部分确认时报告仅引用已确认成员。pending 表示未决，by-design/rejected 是已处理但不纳入问题清单，skipped 是未完成评估；可先导出显式标明未决计数的草稿，最终报告须满足所声明审阅范围的完成条件。若继续采用严格二态 final gate，应在 UI 解释限制和转换操作，不能让用户无法收敛。

建议在审阅页展示并排截图、动作、预期/实际、技术信号、回放结果、调查假设；支持备注与严重度/分类调整，并保留决定版本。报告由确定性模板保留真实证据，LLM 只辅助文字组织，不补造缺失截图、console、network 或步骤。审核改变时旧报告标记过期，再生成当前版本。HTML 使用内嵌图片或随包相对引用，PDF 以同一审阅版本生成，包含环境、范围、未完成项、复现说明和黑盒调查边界。

**关闭条件**：用户处理确认/驳回/备注、重新审核、部分成员采信和 pending；另一目录/电脑打开报告仍显示图与信号；PDF 长步骤和截图分页人工核对。建议审阅/报告职责在 G3 验收。视频是可选产物，未录制时如实注明，不作为每个报告的硬前置。

### C07 [P1] “产出 N 条证据”不能证明发现有效，必须先固定效果与成本分母—评估视角

**组员质问**：“你可以产出很多可疑项，但比固定点击脚本多发现什么？是误报多了，还是审阅者更省时间？模型失败的 run 算在哪里？”

**作者最佳回应**：

> “对**已知注入的 bug**（白屏、hover 缺失、控制台报错）能稳定命中为 `SUSPECT`。”——[总体 §13](../../PLANBOOK.md)。
> “不追求"零误报"——误报由人工审核兜底。”——[总体 §2.2](../../PLANBOOK.md)。
> “分角色用不同档位模型、限制截图大小、按步骤记账”——[总体 §12/API 成本](../../PLANBOOK.md)。

检查：引文占比达标；事实一致性通过；回应部分，明确质量方向，但未给共同样本、对照和审阅/费用口径。

**判断与修改**：成立，属于进入试点的验收定义缺口。建议按 §5 建立固定 benchmark；技术异常与直觉不一致分开统计，不把后一类的主观争议伪装成“真实 bug 标准答案”。Mock 回归证明逻辑、真实模型验证效果；两者分别发布。

**关闭条件**：同一环境/版本/预算的对照结果、完整 run 失败记录、独立标注和成本账单可复核，效果阈值在调 prompt 前约定。建议评估职责与开发接收者在 G2 签认口径，达到事先选择的 gate 才进入 G3 的真实试点交付。

### C08 [P1] 从干净安装到任务终止再到报告发布，需要可观察的生命周期—运维与接入视角

**组员质问**：“新环境没克隆基线仓库，测试能跑吗？扫描超时后实际还在用浏览器/模型吗？原 run 的迟到结果能覆盖新 run 或过期报告吗？”

**作者最佳回应**：

> “**预算控制**：步数/时间上限，耗尽即停。”——[06 §4](../../planbooks/06-action-planner.md)。
> “用 Git 统一协作，保证每个改动可追溯、可回滚。”——[治理 §1](../governance.md)。
> “建议引入 `pre-commit`：提交前自动跑 `ruff` 与 `pytest`。”——[治理 §8](../governance.md)。

检查：引文占比达标；事实一致性通过；回应部分，目标已有，但任务终态、资源释放、可移植测试和发布证据需要具体化。

**判断与修改**：成立，属于跨入口/worker/run 存储的事件裁决缺口。本轮修复必须验证：创建 run 前完成输入与模型配置检查；启动期间即占用该 run 的执行权；停止/超时后进入明确终态，迟到结果不得发布为成功或解除另一 run 的占用。若模型调用不可立即中断，UI 说明正在停止并阻止同一资源并发；浏览器/静态服务释放有可观察结果。重启后孤立 running 记录改为 interrupted，不宣称恢复了不存在的执行进程。

工程交付建议将依赖、浏览器安装和运行说明纳入干净检出验收；普通单元/本地 fixture 测试默认无需真实 API 和外部基线；真实基线测试显式启用、缺资源时给明确信息。CI 区分不联网单测、真实 Chromium fixture 与可选外部环境，报告 skip 和失败原因。发版记录版本、变更、支持范围和 artifact schema；兼容旧 run 则测试读取，不兼容则明确迁移/拒绝策略，不要求此刻无条件迁移到 SQLite。

**关闭条件**：停止/超时/重启/双提交/迟到完成、生成报告后重审、干净检出六类集成场景；CI 与文档准确描述已验证环境。建议入口/运行管理/工程职责在 G1 建立，G4 发布验收。

### C09 [P2] 团队共享和商业权限必须晚于可信结果，不能靠占位模块代替价值验证—产品负责人视角

**组员质问**：“报告还不能稳定复现时，先做账户、权限和收费解决哪项用户结果？本机的环境变量和文件运行模型凭什么直接改成多人服务？”

**作者最佳回应**：

> “现在**不设计定价/支付/账户**，只预留"插槽"与扩展点”——[商业化目标](../commercialization.md)。
> “**只计数不收费**：用量计量埋点只记录数据，不触发任何扣费/限制。”——[商业化 §1](../commercialization.md)。
> “多审核人协作与权限。”——[12 §9/开放问题](../../planbooks/12-human-review-report.md)。

检查：引文占比达标；事实一致性通过；回应充分，商业能力已明确延期，本挑战撤销对“应立即做商业权限”的缺陷认定。

**可守住的取舍与关闭条件**：本地版本先完成 G1～G4；保留成本计量即可。只有出现已验证的团队共享需求，并明确 run 所属、审核冲突、凭据/产物隔离、恢复与资源调度后，才进入团队模式。具体账户人数、组织权限、SaaS 部署和费用规则均未批准，不据此增加本阶段工作。建议产品/运维职责在 G4 后依据试点反馈作单独决策。

阶段是验收闸门，不是人日或上线日期承诺。责任列是所需职责，当前未指定真实人员。

| 阶段 | 主要工程工作与产物 | 进入依赖 | 整体通过条件 | 所需职责 |
|---|---|---|---|---|
| **G1：本地可信闭环，P0** | 收口本轮六项修复；冻结 step/run/evidence/replay/review/report 交接规则；固定 fixture 与失败/停止回归 | 可安装环境、被测 fixture、角色可注入 stub；本轮结果逐项回填 | 单次多步扫描可追溯，判定失败可见，回放起点完整，Issue 隔离，最终报告只消费当前有效审核；停止/超时无迟到成功 | 流水线、LLM、证据/回放、UI、工程、验收 |

## 5. 真实应用与效果 benchmark

### 5.1 真实框架接入矩阵

沿用基线文档作为候选清单，并在真正执行前固定提交、依赖、运行命令、种子数据与复核日期。下面是计划，不是本次已启动或已验证的环境。

| 路径 | 候选环境 | 必须走过的用户场景 | 需要保存的证据 |
|---|---|---|---|
| Next.js | calcom/cal.diy 主选；dub 仅备选 | 带登录态打开业务页、客户端路由、表单校验、modal；source mode 正确选择主应用 | 提交/构建标识、启动与数据重置配方、路由采样、run、角色输入、回放与报告 |
| React SPA | twentyhq/twenty 主选 | React/Vite SPA 路由、异步列表、表单/筛选、动态控件；排除后端和卫星应用 | 主应用选择审计、访问轨迹、状态图、动作窗口信号、样本结果 |
| Vue | chatwoot/chatwoot 主选；nocodb 仅备选 | Vue 动态更新、对话/列表/表单、弹层、登录态过期；黑盒调查 | 会话与数据前置说明、Evidence/Issue 关联、黑盒假设、跨环境回放结果 |

这三个环境的后端/数据服务是本阶段真实接入成本的一部分，不能用 framework 字符串识别或静态 HTML fixture 代替。若主候选暂不可运行，可用固定版本的框架小应用验证机制，并单列“框架机制已验证、真实候选未完成”；不得据此宣称该复杂应用支持完整。基线描述中的版本/许可边界须在执行时重新核对，本阶段不复制其历史命令当作已验证安装指南。

### 5.2 样本、对照与数据规则

1. 建立带 manifest 的固定样本集：应用版本、输入模式、会话/种子数据、视口、预算、模型与 prompt 版本、采样次数、故障注入位置、可达前置条件和重置步骤。已知答案只在评估侧，禁止进入 Explorer/预期生成。
2. 技术异常正样本包括白屏、JS 异常、接口/资源失败、加载不结束；交互正样本包括缺少反馈、误导文案、modal 空内容。配对正常样本包括成功反馈、合法禁用、空数据状态、预期登录跳转等，避免只测有 bug 页面。多步路径覆盖填表/校验/确认/路由，不只测一次 click。
3. 技术缺陷由可运行断言与人工核对建立 ground truth；直觉不一致由独立审阅标注并记录分歧，只有一个审阅者时标为单人探索结果，不声称一致性已证实。重复表象按唯一缺陷去重；聚类误并和误拆另行统计。
4. 对照至少包含相同预算下的固定/贪心动作策略，比较当前探索策略的新增收益；人工流程作为审阅成本的参照。不同模型、采样次数、视觉开关和回放策略的比较使用相同样本与预算；报告失败和未完成 run，不只挑成功记录。
5. 重复真实模型运行估计波动；重复次数、模型预算及最终通过阈值在执行前选择并记录。此文不虚构已有样本量、发现率或费用。既有 mock 结果与真实模型结果分开呈现。

### 5.3 指标与推荐 gate

| 指标 | 分子 / 分母与采集方式 | 防止误解的约束 |
|---|---|---|
| 发现率 | 产生可核对可疑证据的唯一已标注缺陷数 / 在冻结环境中人工确认可达的已标注缺陷总数 | 探索没走到的缺陷仍在分母；环境不可用项在运行前判定并单列；技术/直觉样本分别报 |
| 误报率 | 审阅认定为正常或可接受的候选 Issue 数 / 已完成明确审阅的候选 Issue 数 | pending/skipped 不当成正确候选；同时给未决数、候选总数和 Issue/Evidence 去重口径 |
| 复现率 | 原缺陷条件再次出现的已确认 Issue 数 / 被安排回放的已确认 Issue 数 | blocked/error 计入整体分母并单列；另报可执行回放条件下的成功率；截图相似不自动等于复现 |
| 审阅成本 | 完成审阅的主动操作分钟数 / 已处理候选 Issue 数；另报每个确认问题的分钟数 | 区分查看证据、等待回放和更正聚类；记录中位数及长尾，不以总 UI 打开时间代替 |
| 模型成本 | 每个 run/角色的调用数、输入/输出 token 与可核实费用；另报每个确认且可复现问题的总费用 | 包含重试、fallback、观察、调查、报告；供应商未返回费用时注明估算来源，不能填零 |
| 探索与完成性 | 到达的标注状态/交互覆盖、执行成功率、判定成功率、停止原因、失败 run 数 | 覆盖率分母来自固定样本，不把未知完整网站覆盖率伪装为已知；无证据不等于无问题 |
| 去重与调查质量 | 标注同因/异因对的误并/误拆数；调查结论有证据支撑及可执行步骤的比例 | Root Cause 仍是 hypothesis；黑盒“现象级定位”单列，不能与源码组件定位混算 |

**建议门槛，尚未批准**：G1 对固定确定性 fixture 的链路完整、状态一致和 artifact 可读性要求全部通过；其目标是逻辑正确，不是模型效果百分比。G2 相对同预算基线要求发现率改善且误报、审阅成本不恶化，费用在执行前约定的预算内；若收益只集中于某类样本，发布支持范围限制到该类。直觉类可接受误报率、复现率和每个确认问题费用的具体数值，应由试点任务的重要性和首轮基线共同确定后冻结，不能照抄未测得的数字。G3 要求交付样本的截图、环境、步骤与审核版本完整可读。

## 6. 审阅 UX、报告和外部交付

最小审阅路径是“看 Issue 摘要 → 展开关联证据 → 并排核对前后图与信号 → 查看/执行回放 → 确认、驳回或暂缓并备注 → 预览报告范围 → 导出”。默认按影响与证据完整性排序；低完整度或判定失败的项显式显示，避免用户把它们当正常结果。支持基于严重度、分类、状态与页面筛选，批量决定只作用于用户看到的范围。Issue 合并/拆分和成员采信变化需要重新检查调查与报告版本。

报告至少列出 run 输入模式、被测环境/构建、探索预算和终止原因、判定失败/未覆盖范围、当前审核版本、确认问题清单、真实截图/技术信号、完整复现前置和步骤、回放状态及调查假设。原始产物缺失时明确缺失，不用生成的叙述填补。没有确认问题也可输出范围报告，但结论须区别“完成检查未确认问题”与“因失败/预算未完成”。

HTML 首先提供可移交的单文件或完整目录包；PDF 从相同数据版本打印，人工检查长列表分页、截图可读性、中文字体、页边距与链接。最终交付验收要在第二目录或第二环境打开，不能只在原运行目录中用绝对文件路径查看。

GitHub Issue/Jira/Linear 是 12 的既有远期承诺。G3 可先提供不联网的结构化导出或 Markdown 工单草稿，含 Issue ID、证据引用、环境与审核版本。真实外部写入在用户明确选择目标和授权后单独接入，处理重复创建/重试和撤回；本轮不创建工单、不发送报告。

## 7. 本地发布、团队分界与非目标

当前交付边界是可信本机运行：用户管理应用环境、登录态与模型配置；单进程使用本地产物；Flask 控制台服务本机操作。增加监听地址不代表具备团队服务能力。G4 的安装/使用说明应分别写清源码配方、已运行 URL、会话采集/失效、浏览器依赖、模型检查、预算/停止、历史产物、回放和导出。CI 与报告不能混淆“支持”“测试跳过”“仅规划”。

进入团队模式前另行确定：run 和项目归属；同一 Issue 两人审核的版本冲突裁决；共享产物访问与会话秘密保管；模型配置隔离；执行队列与资源释放；进程重启与状态恢复；存储格式/迁移、备份和删除边界。建议先用共享报告和明确交接验证协作需求，再决定集中服务。SQLite 与目录存储的选择由查询、恢复和并发需求决定，不为了与架构图一致而抢先重写有效本地存储。

本阶段非目标：自动修复、精确像素回归、单元/接口/性能/安全扫描产品、全网站覆盖承诺、零误报承诺、所有 Git/zip/docker/CI preview 输入适配一次交齐、OS 自动化插件、LangGraph 迁移、完整 React tree/git diff 调查、自动拉取第三方环境、线上多租户、账户/定价/支付/许可证服务器。01 的输入适配承诺仍保留在原计划中；先交付本地目录/已运行 URL，再按真实接入需求分别验收其他 adapter。商业化只保留解耦原则与必要的用量计量，不先实现准入限制。
